# 4. 技术栈与选型

## 4.1 选型原则

- 适合单个内部系统和一条主业务链路，不按多团队微服务来拆。
- 优先使用文档全、招人容易、后续一年仍好维护的组合。
- 长任务（分析、搜索、渲染快照）和页面请求分开，避免一次生成拖死页面。
- 供应商可替换：模型和搜索都走适配层，业务表不绑定某一家响应格式。
- 有未确认规则的地方，用数据和校验留下扩展点，不引入规则引擎、工作流平台或低代码运行时。

## 4.2 推荐组合

| 层次 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | TypeScript | 页面、接口、任务进程和结构校验共用类型，减少提案模块前后端各写一套 |
| Web | Next.js（App Router）+ React | 内部页面和客户只读页在同一个项目；服务端渲染适合提案预览和分享页 |
| 样式 | 本系统界面用一套现成组件库即可 | 提案 HTML 的版式与后台皮肤分开。后台换肤不应改客户提案 |
| 模块正文 | 受限富文本（建议 TipTap），输出 JSON，而不是随意 HTML | 满足改文案，同时能过滤脚本 |
| 接口形态 | 同一应用内的 HTTP API | 页面和以后的任务进程都调用明确的服务函数；不另起一个空壳 BFF |
| 数据库 | PostgreSQL | 项目、版本、报价、任务都是关系数据；金额用十进制，不用浮点 |
| 访问库 | Prisma 或 Drizzle 二选一，实现时定一种 | 都成熟。更看重迁移手写可控就用 Drizzle；更看重配套工具就用 Prisma。不要两个一起用 |
| 异步任务 | Redis + BullMQ，独立 worker 进程 | 分析、搜索、渲染都可能超过页面超时；失败可重试、可查询 |
| 文件 | S3 兼容对象存储。本地用 MinIO | 客户素材和冻结 HTML 不进数据库大字段 |
| 登录 | 会话 Cookie（HttpOnly、Secure）+ 口令哈希 | 内部系统，MVP 不做公开注册。具体身份源等 Q12 |
| 结构校验 | Zod（或等价库） | 模型输出先校验再入库 |
| 部署 | Docker Compose | 一台应用、一个 worker、Postgres、Redis、对象存储即可。见第 8 篇 |
| 测试 | 单测 + API 集成测试 + 少量浏览器端到端 | 见第 8 篇 |

Node.js 使用当前 LTS。锁版本写进仓库，不追最新大版本。

### 建议的仓库形态

单包应用，而不是 monorepo。

```text
apps 和 packages 拆分先不做。
src/app          页面与路由
src/server       业务与适配器
src/worker       队列消费者
```

worker 与 web 共用 `src/server`，避免把领域逻辑复制两份。

## 4.3 已经可以定的技术决策

这些决策不依赖未提供的报价公式和组织架构。若审查否定某一条，对应章节要一起改。

### D1 提案的源数据是模块文档，HTML 是渲染结果

客户要的是 HTML，但编辑、替换案例、投影报价都无法稳定地作用在任意 HTML 字符串上。

- 草稿期：模块行 + 类型化 JSON。
- 发布期：除模块快照外，再渲染一份 HTML 文件放入对象存储，分享页优先读这份冻结文件。
- 后台预览走同一套渲染函数，避免预览和交付两套模板。

因此「模块化编辑 HTML」在实现上是编辑模块并重新渲染，不是把整页源码当作数据库。

### D2 搜索是适配器，不是爬虫

业务要求全网搜索图片、视频和创意案例。落地方式是接入一家（先一家）搜索 API，统一成内部候选结构：类型、标题、落地 URL、缩略图 URL、摘要、供应商、原始排名。

视频默认保存外链和标题，不在 MVP 下载转存整段视频。图片是否允许把缩略图存进对象存储，等 Q3。未确认前，规划按「预览时使用供应商返回的地址，发布快照时记录来源 URL」处理，并接受外链失效这一已知限制（第 3 篇异常）。

### D3 金额不由模型生成

在 Q5 给出费率表和公式之前：

- 模型可以产出空的科目建议，供人删除或改名。
- 单价、总价、税率、利润率没有默认常数。
- 利润区在公式配置存在之前显示未配置。

这不是财务制度，是防止系统编造客户可见价格。

### D4 长任务与页面分离

分析、搜索、整稿生成、单模块生成、发布渲染都进队列。HTTP 请求只负责入队和查询状态。worker 写库。页面轮询或刷新任务状态即可，MVP 不必上 WebSocket。

### D5 交付绑定快照

分享令牌指向快照 ID，不指向草稿。渲染文件和快照一起保留。应用回滚不会改写已经生成的 HTML 文件。

## 4.4 替代方案

| 方案 | 何时更合适 | 不作为默认的原因 |
| --- | --- | --- |
| 独立后端（NestJS）+ 独立 React 前端 | 已经有人专职维护 API，且短期会有第二个客户端 | 以当前范围，多一套服务和鉴权，收益不明显 |
| Python FastAPI + React | 团队主要写 Python，或生成链路会大量用 Python 生态 | 两门语言，提案编辑仍要在前端做。若确认团队只熟悉 Python，可以改选，数据模型和 API 清单仍适用 |
| 直接把模型 HTML 存进数据库，用代码编辑器改 | 看起来更「能编辑 HTML」 | 无法稳定替换一个案例或保证报价一致，安全面更大。与 D1 冲突 |
| Word/PPT 作为主交付，再附 HTML | 客户合同指定 Office | 与已确认的 HTML 交付冲突。可作为第二阶段导出，不替换主交付 |
| 无队列，请求里同步调用模型 | 希望少一个 Redis | 生成时长不可控，超时后用户无法判断是否写库。以这条链路的等待时间，队列是必要复杂度，不是多余组件 |
| Kubernetes、服务网格、独立搜索集群 | 多环境、多团队、弹性伸缩成为事实之后 | 当前规模用 Compose 或单机容器更易维护 |
| 低代码表单平台做内部端 | 只想先收集需求 | 做不到模块化提案渲染、快照和案例选用 |

若团队技术背景与 TypeScript 不符，应在开工前改选型，而不是上线后再迁。此项记入 Q13。

## 4.5 主要技术风险

| 风险 | 影响 | 规划中的控制 | 仍需业务确认 |
| --- | --- | --- | --- |
| 网络案例的版权和平台条款 | 客户提案中的图片、视频可能不能转存、不能去水印、不能声称为自有案例 | 记录来源和授权状态；默认外链；人工选用；页面标注外部参考 | Q3：允许的使用方式 |
| 搜索 API 覆盖不了「全网」 | 某类视频站点或中文社区搜不到 | 产品文案不承诺无死角全网；允许手工补链；先接一家，第二家作为适配器扩展 | Q3：第一家供应商和必须覆盖的站点 |
| 外链失效或防盗链 | 交付后图片裂开 | 快照保留来源；预览失败可替换；是否在发布时抓取副本等 Q3 | Q3 |
| 客户素材发送到模型供应商 | 未公开创意和成片脚本离开公司网络 | 适配层集中出口；可按项目关闭「素材出域」；关闭时只把需求正文和文件名送入分析 | Q2 |
| 模型输出不稳定 | 模块缺失或字段越界 | 结构校验失败即任务失败；不覆盖旧草稿 | 无，按此实现 |
| 长视频上传和播放 | 对象存储流量、浏览器播放兼容 | MVP 以原文件存储和基本播放为限；转码不在 MVP | Q10 |
| 提案版式被模块模型限制 | 个别客户要完全自由排版 | MVP 接受模板化专业版式；自由 HTML 放在第二阶段 P8 | 若第一期就必须自由排版，D1 要重审 |
| 报价规则迟迟不确定 | 利润功能无法验收 | 功能上分开「录入」和「按公式计算」；公式未配置不算做完 M21 | Q5 |
| 单包 Next.js 把页面和任务耦在一起 | worker 误引入浏览器代码 | 约束：`src/server` 不引用客户端组件；构建时分开入口 | 工程规范，不是业务待确认 |
| 密钥进仓库或进前端包 | 搜索和模型额度被盗用 | 只放环境变量，服务端调用。见第 6 篇 | 无 |

没有把「换一家更强的模型」列为风险对策。质量问题先靠结构化校验、人工编辑和可重试解决。
