# 1. 项目目标、目标用户、核心使用场景

## 1.1 项目要解决的问题

内部团队接到客户需求和素材之后，需要产出三份彼此一致的结果：

1. 一份客户能看的专业 HTML 提案。
2. 一份只在内部使用的成本与利润核算。
3. 一份审核通过后可以执行的任务拆解。

今天这三份结果如果靠聊天记录、散落素材和手工排版拼出来，案例难追溯、报价和方案容易对不上、改一版就要重做整页。系统要把这条链路收成一个可编辑、可预览、可审核、可留版本的内部流程。

这句话是对已确认需求的归纳，不是额外的商业承诺。

## 1.2 项目目标

### 已确认的产品目标

- 内部人员在 Web 系统中完成从需求录入到审核交付的主路径。
- 客户看到的交付物是 HTML 提案，内容覆盖创意、案例、视觉风格、分镜参考、制作流程、报价、项目排期。
- 案例可以来自客户素材，也可以来自全网搜索到的图片、视频和创意案例。
- 提案按模块编辑，而不是只重新生成一整段不可拆的正文。
- 同一项目内能做成本利润核算，并能生成执行任务。
- 未审核通过的方案不能作为对客户的正式交付。这一点来自「审核后交付」。

### 合理假设的成功标准（待确认后才作为验收指标）

下列数字都还没有业务确认，不能当作本期 KPI。审查时只需要决定要不要测量、以及目标值是多少。

- 从「需求与素材齐备」到「可送审的提案初稿」的人工整理时间是否下降。
- 送审稿中，报价模块与内部报价行是否一致。
- 已交付版本是否都能回溯到当时的 HTML 快照、选用案例和审核记录。
- 搜索结果是否经过人工选用后才进入客户可见提案。见第 3 篇中的假设规则 R-A1。

### 非目标

这些不是本期要证明的事：

- 用系统替代剪辑、设计和投放工具。
- 自动向客户报出可成交价格。模型不准自行编造报价数字，见第 4 篇决策 D3。在费率表确认之前，报价格由内部人员填写。
- 把全网内容爬进自有媒体库后任意再分发。搜索是「找参考并经人工选用」，不是自建抓取平台。
- 对外售卖多租户 SaaS。

## 1.3 目标用户

### 已确认

- 主要使用者是公司内部人员。系统形态是内部 Web 系统。
- 客户是需求与素材的提供者，也是 HTML 提案的接收者。
- 客户是否拥有系统账号：**待确认**。需求只要求把方案交付给客户，没有要求客户登录。

### 合理假设的内部角色

公司编制未知，所以角色按职责命名，不按岗位编制写死。一个人可以兼任多职。MVP 是否拆成这些角色，见待确认 Q4。

| 职责 | 在系统里做什么 | 不做什么 |
| --- | --- | --- |
| 需求负责人 | 建项目、录入需求、上传客户素材、跟踪进度、发起交付 | 不单独决定利润是否对客户可见 |
| 方案编辑 | 确认 AI 分析、选用案例、编辑模块、预览 | 不绕过审核把草稿标成已交付 |
| 报价人员 | 填写成本与对客报价，查看利润 | 不改已交付快照里的历史报价 |
| 审核人 | 看送审快照，通过或退回 | 不在审核动作里直接改客户可见正文 |
| 管理员 | 账号、停用、系统级配置 | 不把密钥写进页面配置 |

在 Q4 确认前，权限矩阵只作为第 6 篇的假设方案。

### 客户侧（待确认 Q1）

两种可能，本规划默认按第一种做页面划分，第二种放到第二阶段：

1. **合理假设**：客户不登录。内部发布后，用带有效期的链接把冻结的 HTML 交给客户。
2. 客户登录后批注、确认。这会改变权限、数据和页面，不进入 MVP，除非 Q1 明确要求第一期就要。

## 1.4 核心使用场景

每个场景只描述已确认流程里的一段。参与者使用上一节的职责名，正式角色名等 Q4。

### 场景 A：收下需求并得到可编辑初稿

- 触发：内部人员拿到客户需求说明和素材。
- 路径：建立客户与项目 → 写入需求正文 → 上传素材 → 发起 AI 分析 → 查看结构化分析 → 人工确认或改正 → 按分析生成检索 → 浏览图片、视频、创意案例 → 选用或弃用 → 生成提案草稿。
- 成功：项目里有一份由模块组成的草稿，预览能看到已确认内容类型（创意、案例、视觉风格、分镜、流程、报价、排期）。报价格可以为空，等待人工填写。
- 搜索无结果或 AI 失败时，项目仍可保存，允许手工补链接、手工写模块。见第 3 篇异常。

### 场景 B：把初稿改成能送审的提案

- 触发：草稿的文案、案例或结构不达标。
- 路径：按模块改文案、隐藏或调整顺序、替换图片或视频、必要时只重做某一个模块 → 预览 → 再改。
- 成功：编辑的是模块内容，预览同步变化；客户素材和网络参考在提案里可区分。区分方式是假设 R-A2，待确认。
- 不在本场景：直接把整页改成不受约束的 HTML 字符串。整页源码编辑不在 MVP。

### 场景 C：核算成本与利润，并写进对客报价

- 触发：方案范围足够判断工作量，需要内部核算。
- 路径：录入成本项 → 录入对客报价项 → 系统按**已确认公式**计算利润 → 选择哪些报价项出现在 HTML 的报价模块。
- 成功：内部能看到成本、报价、利润；客户 HTML 只含被选入提案的报价，不含成本明细和利润。这是假设 R-A3。
- 阻塞：利润公式、币种、税率、成本科目都还未确认（Q5）。确认前只保留数据结构和「可计算」的位置，不预设公式。

### 场景 D：拆执行任务

- 触发：方案和报价范围需要变成可执行工作。
- 路径：基于当前提案生成任务草案 → 人工增删改、指定负责人和日期 → 确认任务列表。
- 成功：任务挂在项目上，能看出哪些是建议、哪些已确认。
- 阻塞：服务目录和任务模板未确认（Q6）。MVP 必须支持手工维护任务；自动草案可以先按通用阶段生成，具体行业模板等目录确认后再配。

### 场景 E：审核后交付

- 触发：编辑认为提案、报价和任务可以送审。
- 路径：发布一份不可变快照 → 提交审核 → 审核人只审这份快照 → 通过后生成交付链接；退回则回到编辑，改完重新发布再审。
- 成功：客户打开的是审核通过的那一版 HTML，而不是之后又改过的草稿。
- 已确认约束：先审核，后交付。
- 待确认：审核是单人还是多级（Q7）；退回后旧链接如何处理（Q8）。

### 场景 F：交付后继续迭代

- 触发：客户反馈要改文案、案例、报价或排期。
- 路径：在不改写已交付快照的前提下产生新版本 → 编辑 → 必要时重算报价和任务 → 再次审核 → 再次交付。
- 成功：旧交付仍可追溯；新交付指向新快照。
- 这是假设 R-A4。若业务希望交付后直接覆盖同一链接，需要在 Q8 改这个假设。

## 1.5 场景之间的数据关系

三个输出必须指向同一项目、同一提案版本，避免「客户看到的报价」和「内部任务所依据的方案」不是一版。

```text
项目
├── 需求正文 + 客户素材
├── AI 分析（可多版，有当前确认版）
├── 搜索与选用的案例
├── 提案草稿 ──发布──▸ 提案快照（客户 HTML 的唯一来源）
├── 成本项（仅内部）
├── 报价项 ──选择后投影──▸ 快照中的报价模块
├── 利润（仅内部，由已确认公式从成本和报价得出）
├── 执行任务（关联送审或交付时所依据的快照）
└── 审核记录 + 交付记录（只绑定快照，不绑定草稿）
```

## 1.6 本篇假设清单

| 编号 | 假设 | 若不成立 |
| --- | --- | --- |
| R-A1 | 网络搜索结果先进入候选，人工选用后才写入客户可见提案 | 需另定自动入选规则和质量门槛，MVP 不建议 |
| R-A2 | 网络案例在 HTML 中标注为外部参考，并保留来源；不得默认显示成公司过往作品 | 需确认公司自有案例库的认定方式 |
| R-A3 | 成本与利润只对内部授权人员可见，不进客户 HTML | 若客户合同要求展示成本结构，报价模块要单独设计 |
| R-A4 | 已交付快照不可原地修改；迭代产生新版本并重新审核 | 若允许覆盖，交付追溯和审核都会改 |
| R-A5 | 界面与提案正文默认中文 | 若要双语或英文提案，模块字段要增加语言 |
| R-A6 | 单公司内部使用，不做多租户 | 若要给多家外部公司开账号，隔离模型要重做 |
